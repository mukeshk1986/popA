1. Solution Design Summary
1.1 Business Purpose
The Risk Engine computes CMS Medicare Advantage (MA) Risk Adjustment scores for health plan members. It ingests raw claims, enrollment, and supplemental data from health plans, transforms and standardizes it, then applies three CMS actuarial models:
* CMS HCC (Hierarchical Condition Category) — community and institutional risk scores
* CMS RxHCC — Prescription Drug Plan risk scores
* CMS ESRD — End-Stage Renal Disease risk scores
The output risk scores drive actuarial calculations worth $8–12 billion in annual Risk Adjustment revenue for MA health plans.

6.3 Qualifying Claims Rules
CMS requires claims to meet specific criteria to be used in risk adjustment. The qualifying_claims.py notebook applies these rules:
Facility Claims Qualification:
* Must have valid facility type code
* Must have valid diagnosis code (ICD-10)
* Service date must fall within the lookback period
* Claim status must be paid/final
* Duplicate claim lines removed
Professional Claims Qualification:
* Rendering provider must have valid NPI
* Claim must not be a non-covered service
* Valid procedure and diagnosis codes required
MAO-004 Supplemental Qualification:
* CMS MAO-004 attestation records
* File type: mao_supplemental_dx
* Filtered for valid ICD-10 codes only

8. CMS HCC Risk Score Calculation
8.1 Overview
The CMS HCC risk scoring model assigns a risk score to each Medicare Advantage member based on their demographic information and diagnosed conditions (HCCs). The platform supports two model versions: V24 and V28.
Entry Point: src/spark/cms/cms_hcc_risk_score_calc.py
Parameters:
ParameterDescriptionenvEnvironmentmodelCMS model code (CMS-HCC)versionModel version (V24 or V28)time_periodDiagnosis lookback period namehome_plan_idHealth plan ID filtercontractCMS contract ID filterplan_namePlan schema prefixsource_load_monthProcessing month (MM)source_load_yearProcessing year (YYYY)incl_supplemental_mmrInclude MMR supplemental data (Y/N)incl_pseudo_claimInclude pseudo-claims (Y/N)8.2 13-Step Calculation Pipeline
The risk scoring follows a precise 13-step pipeline:
Step 1: load_and_prepare_data
- Load risk_member from curation schema
- Load risk_member_diag from curation schema (filtered by time_period start/end dates)
- Load reference tables: coefficient_scores, hierarchy_config, interaction_coefficients, adjustment_factors, icd_hcc_mapping
- Apply HOME_PLAN_ID_CD and CONTRACT_ID filters
- Cache all reference tables for reuse across iterations
Step 2: enrich_claims_with_member_data
- JOIN risk_member_diag with risk_member on BID
- Add member demographic columns to each diagnosis record
- Filter: only members with active enrollment during service period
- Compute AGE at start of risk year: FLOOR(MONTHS_BETWEEN(risk_year_start, DOB) / 12)
Step 3: get_original_disability
- Map OREC (Original Reason for Entitlement Code) to disability status
- OREC = '1' (Age) ? community model
- OREC = '2' (ESRD) ? ESRD model
- OREC = '3' (Disability) ? disability model
- OREC = '4' (Disability + ESRD) ? ESRD+disability model
- Sets community_model flag for downstream coefficient selection
Step 4: assign_community_model
- Determine model segment for each member:
  - CNA: Community Non-Aged (disability)
  - CFA: Community Fully-Benefit Dual Aged
  - CNA: Community Non-Aged/Disabled
  - INS: Institutional (nursing facility)
  - NE: New Enrollee
  - SNPNE: Special Needs Plan New Enrollee
  - PFFS: Private-Fee-For-Service
- Model segment drives coefficient lookup in subsequent steps
Step 5: age_sex_sedits (Demographic Score)
- Assign age/sex coefficients from coefficient_scores table
- Age group mapping: 0-34, 35-44, 45-54, 55-59, 60-64, 65-69, 70-74, 75-79, 80-84, 85+
- Special SEDITS (Sex Edits) processing:
  - SEDITS_DIAG1: D66, D67 (Hemophilia) — male-only condition
  - SEDITS_DIAG2: COPD/chronic bronchitis — gender adjustment
  - SEDITS_DIAG3: C50.* (Breast cancer) — female-only
  - SEDITS_DIAG4: P04.* (Neonatal drug exposure) — pediatric
- Result: demographic_score per member
Step 6: map_icd_to_hcc
- Join risk_member_diag ICD codes against ma_reference.icd_hcc_mapping
- Filter by model version (V24 or V28)
- One ICD code may map to multiple HCCs
- Filter: only valid ICD codes for the current model version
- Output: member-level list of candidate HCC codes
Step 7: apply_hcc_hierarchy_rules
- Apply hierarchy_config to suppress lower-severity HCCs
- If member has HCC_A and HCC_B where A absorbs B ? remove HCC_B
- Example: HCC18 (Diabetes with Acute Complications) absorbs HCC19 (Diabetes without Complications)
- Applies recursively until no further suppressions possible
- Output: final set of payment HCCs per member
Step 8: assign_scores
- Join payment HCCs with coefficient_scores for the member's model segment
- Each HCC has a coefficient (relative risk weight)
- Mark each HCC as IS_PAYMENT_HCC = 'Y'
- Output: HCC-level scores per member
Step 9: add_interaction_rules_and_calculate_score
- Check member's HCC set against interaction_coefficients table
- Disease interactions (V28 examples):
  - DIABETES_CHF: Diabetes + Congestive Heart Failure ? additional coefficient
  - CHF_COPD: CHF + COPD ? additional coefficient
  - CANCER_IMMUNE: Cancer + immune suppression ? additional coefficient
- Add interaction score terms to member's total
- Aggregate: disease_score = SUM(hcc_coefficients) + SUM(interaction_coefficients)
Step 10: calculate_final_scores
- total_score = demographic_score + disease_score
- Store at member level in risk_score table
Step 11: normalization_scores
- Apply CMS normalization: normalized_score = total_score / normalization_factor
- Normalization factor from ma_reference.adjustment_factors
- Separate normalization factors per model segment (community/institutional)
Step 12: weighted_risk_score
- Compute enrollment-weighted risk score per member
- If member enrolled partial year: weighted_score = normalized_score × (enrolled_months / 12)
- Aggregated at contract level for revenue calculation
Step 13: risk_member_hcc processing
- Write detailed HCC-level records to risk_member_hcc table
- One row per member per HCC per model
- Include SCORE_CONTRIBUTION, DIAG_CD evidence, SERVICE_FROM_DT
- Aggregate into risk_member_hcc_summary (member-level HCC list)
- Write/merge risk_score table (final output)

10. CMS ESRD Risk Score Calculation
10.1 Overview
The ESRD model handles members with End-Stage Renal Disease — either on dialysis or post-transplant. Entry point: src/spark/cms/cms_hcc_esrd_risk_score_calc.py.
10.2 ESRD Model Segments
ESRD Model SegmentDescriptionESRD_DIALYSISMembers currently on dialysisESRD_FUNCTIONING_GRAFTPost-transplant with functioning graftESRD_TRANSPLANTMembers who received transplant in current yearESRD_NE_DIALYSISNew Enrollee on dialysisESRD_NE_GRAFTNew Enrollee with functioning graft10.3 ESRD-Specific Transformations (cms_hcc_esrd_transformations.py)
The ESRD model includes special transformations not present in the standard HCC model:
1. ESRD status determination
   ? From MMR ESRD_INDICATOR column
   ? From OREC code '2' (ESRD) or '4' (Disability + ESRD)

2. Dialysis/Transplant flag
   ? Procedure codes: Z99.2 (dialysis dependent)
   ? Transplant codes: T86.1* (kidney transplant complications)
   ? ESRD CPT/HCPCS procedure code lookups

3. Monthly enrollment segmentation
   ? Member may be dialysis in some months, transplant in others
   ? Score computed per enrollment segment

4. ESRD HCC payment suppression
   ? Some HCCs suppressed in ESRD models (already captured in ESRD premium)

11. HCC Persistence Tracking
11.1 Business Purpose
HCC persistence tracks whether a member's diagnosed chronic conditions have been re-documented in the current year. Conditions diagnosed in prior years but not re-documented are "suspect" gaps — a primary input to the gap suspecting engine.
Entry point: src/spark/cms/cms_persistence_hcc.py Logic library: src/spark/cms/member_persistent_hcc.py
11.2 Persistence Parameters
ParameterDescriptionenvEnvironmentplan_nameHealth plansource_load_monthProcessing month (MM)risk_yearCurrent risk yearsource_load_yearData extraction yearprior_yearsNumber of lookback years (default: 2)11.3 Persistence Processing Logic
The persistence engine compares current-year HCC assignments with prior-year history:
Step 1: get_latest_batch_per_cycle_run
  ? Find the most recent completed cycle_run for each prior year
  ? Ensures we compare against the latest available data

Step 2: filter_by_cycle_and_risk_year
  ? Extract HCC records for specified risk_year and prior_years
  ? From risk_member_hcc (current year) and member_persistence_hcc (history)

Step 3: build_src_not_in_tgt (New HCCs)
  ? HCCs in current year NOT in prior year history ? NEW records
  ? Status: 'Open' (newly diagnosed)

Step 4: build_tgt_not_in_src (Dropped HCCs)
  ? HCCs in prior year history NOT in current year ? GAP records
  ? Status: 'Closed' (not re-documented this year)
  ? These become inputs to gap suspecting

Step 5: transform_open_suspects_to_persistent
  ? HCCs present in both current and prior year ? PERSISTENT
  ? Update IS_PERSISTENT = 'Y', update LATEST_CLAIM_DT

Step 6: build_hierarchy_persistent_final
  ? Re-apply HCC hierarchy rules to persistent set
  ? Remove HCCs now suppressed by more-specific codes

Step 7: keep_oldest_by_claim_date
  ? For duplicate HCC records (same BID + HCC): keep oldest claim date
  ? Preserves longest history for compliance documentation

Step 8: merge_update_target_table
  ? Upsert into member_persistence_hcc
  ? MERGE ON (BID, HCC_CODE, RISK_YEAR, CYCLE_RUN)
  ? Update LATEST_CLAIM_DT, STATUS, IS_PERSISTENT
  ? Insert new records
11.4 Persistence Status Values
StatusDescriptionGap Suspecting UseOpenFirst-time HCC diagnosisNot a gap (new condition)PersistentRe-documented in current yearNot a gap (already captured)ClosedNot re-documented this yearPrimary gap suspect inputSuspectCarried forward from prior yearSecondary gap suspect input11.5 3-Year Lookback Window
Risk Year 2025:
  ??? Prior Year 2024: Compare current HCCs against 2024 persistence records
  ??? Prior Year 2023: Extend lookback to 2-year window
  ??? Output: member_persistence_hcc updated for 2025 risk year
